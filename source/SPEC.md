# ImaKuite!Ramen! 仕様書

最終更新: 2026-10-31 ／ アプリ版: `BUILD 2026-10-31-r12` ／ 利用規約版: `2026-10-31-ramen`

旧アプリ「ImaKuite!Inspector!」（飲食店全般。公開中）を土台に、ラーメン専門にしたマッチングアプリ。旧アプリはそのまま残し、サーバ・公開先・端末内の保存を分けている。

## 1. 概要

覆面調査官になってラーメンの感想（食レポ）を投稿し、投稿が将来の自分の「食べたい」を支える、ラーメン専門の食レポ投稿＋好みのマッチングアプリ。

- キャッチコピー: 「今日のあなたの投稿が、未来のあなたの「食べたい」を支えます。」「今日からあなたも、ラーメンインスペクター。」
- 運営者: 株式会社 汗馬の労 ／ 問い合わせ: help@kambanoro.com
- 対象エリア（第1期）: 岡山市中心部（岡山駅を中心に約8km四方）。ラーメン店143件（OpenStreetMap 由来。系統は店名から推定）
- 公開URL: https://kambanoro2685-dot.github.io/imakuite-ramen/
- 対応環境: **Web（スマホ・PCのブラウザ）のみ**。iOS / Android ネイティブは、パスキー・写真・地図が未対応

## 4. 階級とポイント

| 階級 | 必要ポイント | 備考 |
|---|---|---|
| 0 見習い | 0 | |
| 1 三等インスペクター | 300 | |
| 2 二等インスペクター | 1,200 | |
| 3 一等インスペクター | 3,000 | |
| 4 主任インスペクター | 8,000 | |
| 5 特別監察官 | 20,000 | 信頼度 800 以上も必要 |

- ポイントは**サーバが付与**する。クライアントの申告は信用しない。
- 主な加点: 来店 +15（ルーレットで「ここに行く」）、事後評価 +10、初訪問ボーナス +30、写真 +5（1投稿3枚まで）。そのほか、推し皿・清掃5項目・環境・状態・味の分析・接客情報・品質4項目・設備情報・騒音の測定など、入力項目ごとの加点がある。
- 見習いの1投稿の加点上限は48pt（階級による項目解放が効く）。
- 見本データは 0pt。

### 解放される入力項目（全40項目、段階0〜4）

| 階級 | 増える項目 |
|---|---|
| 見習い | 基本8項目（写真・価格・感想など） |
| 三等 | 清掃5項目・静かさ・待ち時間・満腹度など（10項目） |
| 二等 | 5味評価・接客・提供時間（8項目） |
| 一等 | 品質4項目・混み具合・支払い・設備（9項目） |
| 主任 | 騒音の測定・推し皿・来店の目的 |
| 特別監察官 | 指摘の検証キュー（未実装） |

定義は `app/src/data.ts` の `FIELDS` / `RANKS`。

## 5. 他の調査官の評価の見せ方

`shop_reviews`（サーバ関数）が階級に応じて返す内容を絞る。

- 読める範囲: 見習い＝自分が投稿した店だけ（`own_shop`）／三等＝どの店でも直近30日／二等＝全期間の平均値／一等＝全期間・全件・並べ替え／主任＝訂正履歴も。
- 項目ごとの黒塗り: (a) その項目に必要な階級に達していない（🔒 rank）、(b) 閲覧者自身がその項目を一度も入力していない（✏️ input）。黒塗りは `██████` で表示。
- 調査官の名前・IDは出さない。階級と信頼度だけを添える。
- 店の検索結果と詳細には、**調査した人の階級の内訳**（階級ごとの人数）を出す。評価件数と同じく3件以上の店だけ。3件未満は「調査待ち」。
- ルーレットの結果にも、階級の内訳と他の調査官の投稿を表示する。

## 4-2. ラーメン専用の項目

入力項目はラーメン向けに置き換えた（階級で解放される仕組みは同じ）。

| 項目 | 解放 | 保存先（dish） | ポイント |
|---|---|---|---|
| スープの系統（醤油・味噌・塩・豚骨・家系・二郎系・つけ麺・まぜそば・油そば・担々麺・煮干し・魚介・鶏白湯・その他） | 見習い | `soup` | +5 |
| 濃さ（あっさり〜超こってり、0〜4） | 三等 | `richness` | 濃さ・麺の太さ・硬さの3つで +8 |
| 麺の太さ（細・中・太・極太） | 三等 | `noodle_thick` | 〃 |
| 麺の硬さ（固め・普通・柔らかめ） | 三等 | `noodle_firm` | 〃 |
| 麺の種類（ちぢれ・ストレート・平打ち） | 三等 | `noodle_type` | なし（マッチング用） |
| 替え玉（した・しなかった・なし） | 三等 | `kaedama` | なし |
| スープの味5評価（甘み・塩気・酸味・苦み・うま味・辛さ） | 二等 | `taste_*` | 3つ以上で +8 |
| 品質（香り・麺の食感・スープの温度・見た目） | 一等 | `aroma` など | 4つで +10 |
| トッピング（チャーシュー・味玉・メンマなど） | 一等 | `toppings` | +3 |
| 推し一杯 | 主任 | `is_pick` | — |

他の調査官のラーメン項目も、階級で黒塗りされる（スープ=見習い、濃さ・麺=三等、トッピング=一等）。

## 4-2a. 価格の入力

- 価格は、「＋／−」で100円ずつ、「−10円／＋10円」で10円ずつ変えられる。数字を直接入れると1円単位でも入力できる（例: 税込 1078）。数字以外は自動で除き、最大 99,999円。

## 4-2b. 近くの店の候補

- 調査報告書・さがす・ルーレット・地図は、基準点（既定は岡山駅、「現在地にする」で現在地）の近くの店を、近い順に出す。
- まず半径3km。店が6件未満なら、8km → 20km と自動で広げる（画面に「範囲を広げています」と出る）。遠い店は「約N.Nkm」、近い店は「徒歩N分」と表示する。
- それでも店が無い（対応エリアの外にいる）ときは、調査報告書に案内と「岡山駅周辺の店を出す」ボタンが出る。位置情報の取得に失敗したときも、理由が出る。

## 4-2c. 候補にない店の追加

- ラーメン専門店でない店（町中華・定食屋など）や、データにない新しい店は、調査報告書の「店名で探す」欄に店名を入れて「現在地の店として追加」を押すと登録できる（確認の1回あり）。
- いまの場所（位置情報）に店ができ、そのまま選ばれる。新しい店には **+100pt**（サーバが付与）。店の系統は「その他」。
- **アカウントなし（この端末だけ）の人**も追加できる。その店はこの端末の中だけ（`localVenues`）に保存し、サーバには送らず、他の人には見えず、+100ptも付かない。アカウントを登録（ログイン）すると、全員の店リストに載り +100pt になる（アカウントがあるときは、端末だけの店は使わない）。
- アカウントはあるがログインが切れているときは、案内と「ログインし直す」ボタンが出る。
- 同じ名前の店が近く（約100m）にあると重複として弾く。1人1日20件まで。追加した店は、全員の店リストに載る（`create_shop`）。

## 4-3. 好みのマッチング

- 登録時に「好きなラーメン（系統・複数）」「こってり度」「麺の太さ」「麺の種類（ちぢれ・ストレート・平打ち）」「好きなトッピング（複数）」を選ぶ（こってり度・麺・トッピングは任意）。
- 店ごとに**相性%**を出す。系統（重み35%）・こってり度（25%）・麺の太さ（15%）・麺の種類（15%）・トッピング（10%）のうち、分かるものだけで計算する。
  - 口コミが3件以上の店: いちばん多いスープ・濃さの平均・いちばん多い麺の太さ・いちばん多い麺の種類・多いトッピング上位3つ（`search_shops` が返す。トッピングは好きなトッピングとの重なりの割合で見る）。
  - まだの店: 店名から推定した系統だけ（画面に「店名から推定」と出る）。
- 使う場所: さがす（「相性順」と相性タグ）、ルーレット（相性が高い店ほど当たりやすい）、ホームのおすすめ。
- 店名からの系統推定: 家系・二郎系・つけ麺・まぜそば・油そば・担々麺・鶏白湯・煮干し・豚骨・味噌・塩・醤油の順に判定し、分からなければ「その他」。

## 5-2. 推しとランキング

- 調査官は、マイページ相当の「推し」タブで**自分で公開をオン**にしたときだけ、コードネーム・公開ID・階級・ポイント・調査件数・推されている数が他の人に見える（初期値はオフ。オフに戻せる）。
- 公開している調査官を、コードネーム検索かランキングから「推し」にできる（1人20人まで）。誰を推しているかは他の人には見えない。
- 推しが調査した店は、さがす（おすすめ順の上位・「推しの店だけ」・💗タグ）、ルーレット（「推しを優先」）、ホームのおすすめで優先される。
- ランキングは「ポイント順」と「推されている数」。公開している調査官だけが対象。
- アカウントを削除（凍結）すると、公開はオフになり、推しの関係はすべて消える（トリガー）。
- 利用規約の版は `2026-10-31-ramen`（公開と推しの項を追記）。

## 6. 認証・アカウント

- 入り口: 最初の画面で「はじめての方（新しく登録する）」と「登録済みの方（ログインする）」を分ける。新規登録の入力（調査官名・好み・規約同意）と、ログイン（パスキー／復旧コード）は別の画面で、どちらからも「最初の画面」にもどれる。
- 新規登録: 端末の**パスキー**を作成する。裏では、ランダムなメールアドレスとパスワードの Supabase アカウント（Confirm email はオフ）を作る。パスワードは利用者には見せない。
- 匿名ログインでは、パスキー登録ができない（Supabase が拒否）ため、上記の方式にした。
- ログイン: パスキーのみ。RP ID は `kambanoro2685-dot.github.io`。
- 端末だけで使うモードあり（サーバへは投稿しない）。
- **復旧コード**: マイページで発行する `IKRC-<32桁>-<22文字>` の文字列。合成メールと新しいパスワード（128bit）を1本にしたもの。発行時の1回だけ表示し、再発行すると前のコードは無効になる。初回画面の「復旧コードでログイン」で使う。
- メール・ソーシャルでのログインは**未実装**（Supabase 標準のメール送信は組織メンバー宛てに限られるため、一般の利用者へ送るには独自SMTPが要る）。
- アカウント削除: 写真を先に削除し、その後 `delete_account`。投稿は凍結・匿名化（`削除済み-` で始まる名前）し、認証情報は消す。

## 7. 利用規約の承諾

- **最後まで読まないと同意できない:** 登録画面と再同意の画面で、同意のチェックは、利用規約とプライバシーポリシーの**両方を画面の最後までスクロール**するまで押せない（グレー表示。押すと「先に最後まで読んでください」と出る）。読んだ状態は、その画面を開いている間だけ保持する。

- `terms.ts` に規約・プライバシー・運営者情報を持つ。版は `TERMS_VERSION`（現在 `2026-10-23`）。
- 登録時に承諾チェックが必須。版が変わると、全画面の再同意画面（`TermsGate`）が出る。
- 承諾の記録はサーバの `terms_acceptance` に保存（`accept_terms`）。
- 規約の文面は草案。**弁護士による確認は未実施**。

## 8. データベース（Supabase）

マイグレーションは `supabase/migrations/` の 0001〜0011。すべて本番に適用済み。

| 番号 | 内容 |
|---|---|
| 0001 | 初期テーブル、RLS、基本の関数 |
| 0002 | 試験用の店（本番では 0006 で無効化） |
| 0003 | 不具合報告 |
| 0004 | 階級に応じたポイント付与 |
| 0005 | 店舗検索を未ログインにも開放（`osm_id`、`p_limit`） |
| 0006 | OSM の実在ラーメン店143件（岡山市中心部・系統は店名から推定） |
| 0007 | 写真（制約、`photo_count`、写真加点、`delete_account`） |
| 0008 | Storage バケット `visit-photos` とポリシー |
| 0009 | 他の調査官の評価（`shop_reviews`、`_mask`） |
| 0010 | 規約の承諾（`accept_terms`、`me()` に版を追加） |
| 0011 | 検索結果に階級の内訳（`rank_counts`） |
| 0015 | トッピングの集計（search_shops の toppings_top） |
| 0014 | 麺の種類（dish.noodle_type、search_shops の type_top） |
| 0013 | ラーメン専用の項目（dish の列、submit_visit のポイント、shop_reviews、search_shops の集計） |

- 主な関数（すべて SECURITY DEFINER）: `register_inspector, me, submit_visit, create_shop, search_shops, shop_stats, correct_field, delete_account, stats_live, submit_bug_report, shop_reviews, accept_terms, photo_count, _mask`

- 写真: バケット `visit-photos`（公開、1MB まで、webp / jpeg、自分のフォルダだけ書ける）。キャッシュは3600秒。

### 端末内の状態（`store.tsx`）

アカウント（公開ID・パスキー有無）、プロフィール、投稿（`posts`、同期の進み具合 `sync` を持つ）、訪問済みの店（`visited`）、今日の指令（`mission`）、規約の承諾、見本データ。古い数値の店IDは UUID へ移行する。

## 9. 見本データ

地図やマイページの「見本を入れてみる」で、近くの実在店5件の調査記録と今日の指令を端末内に入れる。

- 端末の中だけに保存。サーバへ送らず、ポイントにも数えない。
- 「見本」と表示し、訂正はできない。「見本を消す」でいつでも消せる。

## 10. 好きなラーメン（系統）

醤油、味噌、塩、豚骨、家系、二郎系、つけ麺、まぜそば・油そば、担々麺、煮干し・魚介、鶏白湯（店の系統には「その他」もある）。

## 11. テスト

- DBテスト: `cd imakuite/supabase && npm test`（PGlite。**170件すべて合格**）。Storage と認証はスタブ。
- 本番サーバの e2e: 合成アカウントで実行し、`delete_account` で後片付けする。

## 12. 公開手順

1. `npx expo export --platform web`（`app.json` の baseUrl は `/imakuite-ramen`）
2. 出力 `dist` の中身を、GitHub Pages のクローン（imakuite-ramen の master 直下）に置き換え、ソースを `source/` にコピー
3. コミットして master に push
4. 公開URLの JS ファイル名が新しくなるまで待つ（`.nojekyll` が必要）

SQL は、Supabase の SQL エディタに貼って実行する（新しい migration は、先に `source/supabase/migrations` へ置く）。

## 13. 既知の制限と未実装

- ネイティブアプリ（パスキー・写真・地図）。
- 写真の顔の自動ぼかし。
- 指摘・検証（`report_flag`）と、特別監察官の検証キュー。
- ルーレットのサーバ側管理（指令）。いまは端末内のみ。
- ポイントの仮 → 確定の定期処理、減点、信頼度の自動更新。
- メール・ソーシャルでのログイン（独自SMTPが前提）。復旧コードは実装済み。
- 規約の弁護士確認。
- 店舗データは OSM 由来のため、閉店・移転が反映されていない場合がある。
- 本番の店はまだ調査が3件未満のものが多く、評価件数・階級の内訳が出る店は少ない。
- ラーメン版: 店の系統は店名からの推定で、外れる店がある（口コミがたまると、スープ・濃さ・麺の太さは口コミから出る）。
- ラーメン版: 店の系統でのさがす絞り込みは店名からの推定にもとづく。口コミの系統での絞り込みは未実装。
- ラーメン版: 公開URLでの、パスキー登録と投稿の実機確認は未実施。
